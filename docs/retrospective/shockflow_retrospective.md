# 뉴스로 수요 충격을 잡을 수 있을까: ShockFlow AI 개발 회고

## 출발점

처음 궁금했던 것은 하나였다. 수요예측 모델은 평소 패턴을 잘 맞추지만, 갑자기 생기는 변화에는 늘 늦다. 지하철이 멈추거나, 큰 공연이 열리거나, 폭설이 오는 날의 자전거 수요는 지난주 같은 시각의 수요와 다르다. 그런 변화의 원인은 대개 뉴스에 먼저 나온다. 그렇다면 뉴스에서 이벤트를 뽑아 피처로 넣으면 예측이 좋아질까.

데이터는 공개된 것으로 모았다. NYC Citi Bike 대여 이력, NYC 허가 이벤트 목록 63,070건, GDELT 뉴스, NOAA 일 단위 기상. 예측 단위는 H3 zone 하나와 현지 시간 한 시간이고, 목표는 그 시간의 출발 수다. 모델은 scikit-learn 의 HistGradientBoostingRegressor 로 정했다. LightGBM 을 쓰지 않은 이유는 단순하다. 의존성을 하나 줄이고, 학습한 모델을 그대로 API 에 싣는 데 scikit-learn 파이프라인이 편했다.

이 글은 그 질문에 답하려고 시도하고, 막히고, 바꾸고, 결국 무엇을 배웠는지의 기록이다. 잘 된 것과 안 된 것을 같이 적는다. 숫자는 저장소의 결과 파일에 있는 것만 썼다.

## 기준선부터 만들다

이벤트 피처로 가기 전에 기준선이 필요했다. 지난주 같은 시각의 값을 그대로 쓰는 seasonal naive 가 가장 낮은 기준이고, 그 위에 지연 피처와 달력 피처만 넣은 트리 모델이 두 번째 기준이다.

여기서 처음 시간을 많이 쓴 곳은 모델이 아니라 피처의 시간 규칙이었다. 1시간 전, 24시간 전, 168시간 전 값과 이동 평균을 만들 때 현재 시각의 값이 자기 피처에 섞이면 안 된다. 롤링 창은 집계 전에 한 칸 밀어야 하고, 뉴욕의 서머타임 전환 시각은 조용히 버리면 안 된다. 이 규칙들을 먼저 테스트로 박아 두고 나서야 모델을 돌렸다.

평가는 랜덤 분할을 쓰지 않았다. 시간 순서대로 학습 구간을 늘려 가며 다음 달을 예측하는 rolling-origin 방식이다. 승격한 모델은 저지시티 패널 226,953행, 219개 zone 에서 5월, 6월, 7월 세 창을 돌려 WAPE 0.4974 ± 0.0074 가 나왔다. seasonal naive 는 같은 5월 창에서 0.688 이었으니 트리 모델만으로도 오차의 4분의 1 이상이 줄었다. 그리고 이 값이 뒤에 나오는 모든 실험의 기준이 됐다.

## 이벤트 피처를 넣다, 그리고 첫 번째 환희

허가 이벤트부터 넣었다. 시청이 공개하는 허가 목록에는 시작 시각, 종료 시각, 거리 통제 여부, 자치구가 들어 있다. 이걸 자치구와 시간 단위 셀로 펼쳐 네 개 피처로 만들었다. 진행 중인 이벤트 수, 거리 통제 수, 군중형 이벤트 수, 6시간 안에 시작하는 이벤트 수.

실험 단위는 자치구와 시간이다. zone 단위로 내려가면 허가 이벤트와 뉴스를 정확한 좌표로 붙일 근거가 부족했기 때문이다. 5월 한 달을 홀드아웃으로 두고 비교하니 결과가 좋았다. 수요 이력과 달력만 쓴 모델에 허가 이벤트를 더하자 행당 절대오차가 평균 3.99대 줄었고, 일 단위 블록 부트스트랩 95% 신뢰구간은 [1.08, 6.71] 로 0을 넘지 않았다. 여기까지가 첫 번째 환희였다.

## 재현에 실패하다

한 달짜리 결과를 믿기 어려워 창을 늘렸다. 2월부터 7월까지 여섯 개 창에서 창마다 다시 학습하고 같은 비교를 반복했다. 허가 이벤트의 효과는 0을 넘는 창이 하나도 없었다. 아래로 벗어난 창이 하나, 결론을 낼 수 없는 창이 넷이었다. 5월 한 창에서 유의했던 숫자는 다른 달에서 사라졌다.

그래서 철회했다. README 에 처음 적었던 개선 주장을 지우지 않고, 원래 결과와 재현 실패를 나란히 두었다. 이 결정이 프로젝트의 방향을 바꿨다. 한 창의 유의성은 결과가 아니라 가설이라는 것을 그때 받아들였다.

## LLM 으로 뉴스에서 이벤트를 뽑다

허가 이벤트가 흔들렸으니 뉴스로 가 보기로 했다. GDELT 에서 뉴욕 기사를 모으고, LLM 에게 기사 한 건에서 이벤트 유형, 영향 방향, 심각도, 신뢰도, 지명, 근거 문장을 뽑게 했다. 수요가 몇 퍼센트 변할지는 절대 묻지 않았다. 방향과 0에서 1 사이의 심각도만 받았다.

여기서 어려웠던 점이 셋이었다. 첫째는 근거다. LLM 이 돌려준 인용문이 기사 원문에 정확히 있어야만 이벤트로 인정했다. 원문에 없는 인용은 버렸다. 둘째는 지역이다. 기사에 자치구 이름이 있으면 그곳에만, 이름이 없고 지하철이나 폭설처럼 도시 전역 단서가 있으면 다섯 자치구 전부에, 둘 다 없으면 버렸다. 추측해서 어딘가에 넣지 않았다. 셋째는 개수다. 반년치 뉴스에서 자전거 수요와 관련 있는 이벤트는 23건뿐이었다.

뽑은 이벤트는 네 개 숫자로 바뀌어 모델에 들어갔다. 해당 자치구의 공개 시각부터 24시간 동안 이벤트 수, 심각도 합, 교통 중단 여부, 군중 이벤트 여부다. 영향 방향은 채택된 피처에 넣지 않았다. 방향을 -1 에서 +1 사이 값으로 받아 심각도와 곱한 변형도 따로 돌려 봤는데, 오차가 WAPE 0.0883 에서 0.0906 으로 나빠져서 쓰지 않았다.

누수는 공개 시각으로 막았다. 기사의 공개 시각과 시스템이 처음 본 시각 중 늦은 쪽을 가용 시각으로 두고, 예측 시점보다 늦게 가용해진 이벤트는 그 시점의 피처에서 제외했다. 14시 1분에 공개된 기사가 14시 예측에 0으로 들어가는 테스트를 가장 먼저 만들었다.

나중에 알게 된 허점도 있다. 자치구 실험에 쓴 인덱스 하나가 가용 시각을 시간 단위로 내림해서 켜고 있었다. 14시 30분에 공개된 기사가 14시 셀부터 켜지니, 첫 셀에서 최대 59분을 앞서 보는 셈이다. 개선판 빌더는 셀 시작이 가용 시각보다 빠르면 건너뛰도록 고쳤지만, 대표 숫자를 만든 실험은 옛 빌더로 돌린 것이라 이 점은 밝혀 둔다.

## 조건부로만 효과가 있다

뉴스 피처를 넣고 여섯 창을 다시 돌리자 부호가 창마다 뒤집혔다. 시드 하나로는 믿을 수 없어 시드 열 개로 학습해 예측을 평균했다. 그 결과가 이 프로젝트의 대표 숫자다.

| 창 | 이벤트당 평균 자치구 수 | 전역 이벤트 비율 | 뉴스 피처 추가 시 오차 변화 |
|---|---:|---:|---:|
| 2월 | 4.2 | 80% | −0.96대 (악화) |
| 3월 | 3.67 | 67% | −0.86대 (악화) |
| 5월 | 2.29 | 29% | −0.76대 (악화) |
| 6월 | 2.0 | 25% | **+1.24대 (개선)** |

6월 창에서는 자치구 시간당 절대오차가 평균 1.24대 줄었다. 상대로는 0.69%, 신뢰구간 [0.83, 1.64] 로 0을 넘지 않았다. 시드 열 개 중 일곱이 양수였고 시드 간 표준편차는 2.5 였다. 작지만 분명한 개선이다. 그런데 2월과 3월은 반대였다.

차이는 이벤트가 어디서 일어났느냐였다. 2월의 뉴스는 폭설과 지하철 장애처럼 도시 전역 사건이 대부분이었다. 전역 사건은 다섯 자치구의 피처를 동시에 켠다. 그러면 피처는 어느 자치구가 움직이는지 말해 주지 못하고, 그날 무언가 있었다는 시간 더미가 된다. 달력 피처가 이미 아는 정보와 겹치니 남는 것은 잡음뿐이다. 6월의 뉴스는 펜역 사건, 닉스 우승 퍼레이드, 매디슨 스퀘어 가든 공연처럼 맨해튼 한 곳을 가리켰다. 지역이 특정될수록 피처가 공간 대비를 만들고, 그때만 예측이 좋아졌다.

처음 세웠던 가설 하나는 검증하지 못했다. 뉴스가 사건보다 먼저 나와야 효과가 있을 것이라고 생각했는데, 23건 중 3시간 이상 먼저 보도된 것은 2건, 그중 지역까지 특정된 것은 1건뿐이었다. 뉴스는 대개 사건과 동시에 또는 사후에 나온다. 뉴스를 정확한 시작과 종료 시각으로 재구성해 허가 이벤트처럼 넣는 실험도 해 봤는데 WAPE 가 0.0883 에서 0.094 로 나빠졌고, 사후 보도 4건은 누수 규칙에 걸려 자동으로 빠졌다. 선행성이 중요한지는 데이터에 그런 사례가 없어서 답할 수 없었다.

날씨도 넣어 봤다. NOAA 의 센트럴파크 일 단위 기록을 전날 값으로 붙였더니 6월 창 210개 zone 에서 WAPE 가 0.4868 에서 0.4893 으로 0.51% 나빠졌다. 신뢰구간도 0 아래였다. 일 단위 기상은 시간 단위 수요 이력이 이미 담고 있는 정보였다.

그래서 승격해서 서빙하는 모델에는 이벤트 피처가 하나도 없다. 수요 이력과 달력 32개 피처뿐이다. 조건부로만 개선되는 피처를 기본 모델에 넣지 않기로 했고, 그 판단의 근거를 모두 결과 파일로 남겼다.

## 정확도 대신 비용을 보다

예측이 쓰이는 곳은 재배치다. 자전거가 모자라는 것과 남는 것의 비용은 같지 않다. 모자라면 고객이 떠나고, 남으면 트럭이 헛걸음한다. 그래서 부족 비용 2, 과잉 비용 1로 가중한 운영비용 점수를 만들었다. 뉴스벤더 이론대로라면 비용을 최소화하는 점 예측은 2 나누기 3, 즉 0.667 분위에 있어야 한다.

이 예측을 실험 전에 파일에 적어 두고 돌렸다. 손실 함수만 바꾸고 알고리즘, 하이퍼파라미터, 피처, 창, 시드는 그대로 두었다. 결과는 예측과 맞았다. 세 창 모두에서 0.667 분위가 최적이었다. WAPE 는 0.4974 에서 0.5391 로 8.38% 나빠졌지만, 운영비용은 3.42% 줄었고 품절 단위는 79,772 에서 58,663 으로 26.5% 줄었다. 대신 과잉 단위가 45% 늘었다. 정확도 하나만 보면 나쁜 모델이고, 비용으로 보면 더 나은 모델이다. 어느 쪽을 택할지는 운영의 결정이고, 모델은 두 숫자를 같이 내놓아야 한다는 것을 배웠다.

## 재배치: 탐욕이 무대응보다 비쌌다

재배치는 세 단계로 만들었다. 먼저 가장 부족한 정류장을 가장 가까운 잉여 정류장에서 채우는 탐욕 해, 다음은 scipy 의 HiGHS 로 푸는 단일 시점 MILP, 마지막은 6시간 앞 예측을 보고 매시간 다시 푸는 MPC 다. 8개 zone 에 72시간짜리 시드 고정 통근 시나리오를 만들어 네 정책과 미래를 아는 Oracle 을 같은 장부로 비교했다. 비용 가정은 부족 1.00, 과잉 0.30, 이동 0.40 이고, 출처가 확인된 값이 아니라 가정이라고 파일에 적혀 있다.

총비용은 무대응 1,127, 탐욕 1,155, MILP 1,087, MPC 740, Oracle 719 였다. 탐욕이 무대응보다 비쌌다는 것이 가장 재미있는 결과였다. 탐욕은 부족을 37% 줄였지만 그만큼 트럭을 많이 움직여 이동 비용이 부족 비용 절감을 넘었다. MILP 는 같은 1시간 예측으로 부족을 42% 줄이면서 이동을 덜 해 총비용을 낮췄다. MPC 는 6시간 앞을 보기 때문에 지금 옮길지 다음 시간에 옮길지를 고를 수 있었고, 부족을 73% 줄이면서 Oracle 과의 차이가 22에 불과했다. 정확한 해법이 탐욕보다 나은 이유는 더 많이 옮겨서가 아니라 덜 옮겨도 되는 때를 알기 때문이었다.

## GraphRAG: 쉬웠던 이유와 어려웠을 이유

운영자가 숫자의 출처를 물을 수 있게 하고 싶었다. 기사, 이벤트, zone 을 그래프로 잇고 LLM 이 그 그래프에서 근거를 찾아 답하게 했다. 숫자는 LLM 이 계산하지 않고 도구 호출로 가져오게 했다. 처음에 키워드로 도구를 고르게 했더니 20문항 중 정답률 0.833 에 환각 답변이 3건 나왔고, LLM 라우터로 바꾸자 1.0 에 0건이 됐다.

10문항 점검에서는 검색 없이 답하는 모델이 10건 모두 지어낸 이벤트를 인용했고, 검색은 하되 관련성을 따지지 않는 모델은 4건을 맞혔고, 그래프 관계로 범위를 좁히는 GraphRAG 는 10건을 맞혔다. 여기서 솔직해야 할 것이 있다. 이 세 답변 세트는 채점 설계를 보이려고 손으로 쓴 예시 답변이지 실제 LLM 출력이 아니다. 실제 LLM 답변 10건에 대한 RAGAS 점수는 faithfulness 1.0, answer relevancy 0.985 였는데, 판정도 외부 API 없이 세션 안에서 모델이 한 것이다. 21문항짜리 두 번째 벤치마크에서는 평면 검색이 21건 중 6건, GraphRAG 가 21건을 맞혔지만, 정답이 그래프의 간선으로 정의돼 있어 GraphRAG 가 높을 수밖에 없는 구조였다.

그래프 자체는 쉬웠다. 이벤트는 이미 JSON 으로 정리돼 있었고 자치구 이름과 zone 좌표가 붙어 있었다. 허가 이벤트를 2,000건으로 제한한 빌드가 노드 5,770개, 엣지 11,850개였고 제한을 풀면 노드 8,045개, 엣지 16,540개다. Neo4j 스키마와 Cypher 는 만들었지만 서빙은 JSON 스냅숏으로 하고 Neo4j 는 선택 사항으로 두었다. 이 규모에서는 자치구 태그 하나로 거르는 일반 검색으로도 같은 결과가 나왔을 것이다. 그래프가 진짜 어려운 곳은 관계가 데이터에 적혀 있지 않은 도메인이다. 어떤 이벤트가 어떤 지역에 영향을 주는지를 정의하는 일이 가장 어렵고, 이 프로젝트는 그 일을 지명 사전과 자치구 규칙으로 대신했다.

## 서빙에서 찾은 병목

예측과 최적화 결과는 FastAPI 엔드포인트 31개로 냈다. 요청과 응답은 Pydantic 계약으로 고정하고, 모든 응답에 run_id, artifact_id, 모드, 주장 상태, 생성 시각을 넣었다. 어떤 숫자든 어느 실험의 어느 파일에서 왔는지 따라갈 수 있게 하려는 것이다. HTTP 경계 계약 테스트는 55개, MCP 전송이 같은 답을 내는지 보는 테스트는 9개다.

부하 테스트에서 이상한 것을 봤다. 혼자 요청하면 초당 261건인데 다섯 명이 동시에 요청하면 113건으로 떨어졌다. 원인은 scikit-learn 의 predict 가 요청마다 OpenMP 스레드를 4개씩 띄워 4코어를 초과 점유하는 것이었다. OMP_NUM_THREADS=1 로 스레드를 묶자 포화 처리량이 105 에서 138 req/s 로 31% 올랐다. 워커를 넷으로 늘리면 700 req/s 근처까지 갔다.

첫 요청 지연도 있었다. 0.1 CPU 무료 티어를 흉내 낸 환경에서 첫 요청이 33.3초 걸렸다. 모델 번들과 scikit-learn import 를 첫 요청이 떠안고 있었다. 서버 시작 시 미리 로드하도록 바꾸자 104ms 가 됐다. 입력 행렬을 요청마다 다시 만들던 것도 고쳤는데, 이건 함수 내부 2.8ms 중 0.6ms 를 아낀 것이라 31% 와는 별개다. 도구 호출을 MCP 서버로 분리한 것도 처리량과 무관했다. 전송만 바뀌고 답은 같았으며, 호출당 2.6 에서 4.9ms 가 더 들었다.

## 이 프로젝트에서 배운 것

가장 크게 배운 것은 한 번의 유의한 결과를 믿지 않는 법이다. 허가 이벤트는 5월 한 창에서 신뢰구간이 0을 넘었고, 여섯 창으로 늘리자 사라졌다. 뉴스 피처는 창마다 부호가 뒤집혔다. 시드를 열 개로 늘리고 창을 여섯으로 늘린 뒤에야 "언제 효과가 있는지" 를 말할 수 있었다. 결과를 재현하려는 시도가 결과 자체보다 더 많은 것을 알려 줬다.

둘째, 이벤트 피처의 가치는 이벤트의 공간 해상도에 달려 있다. 도시 전역 사건은 모델이 이미 아는 것을 다시 말할 뿐이고, 한 자치구를 가리키는 사건만 새로운 정보를 준다. 뉴스가 사건보다 먼저 나오는지는 중요할 것 같았지만 데이터에 그런 사례가 거의 없어서 확인하지 못했다. 다음에 같은 문제를 다룬다면 뉴스보다 공연 일정이나 공사 공지처럼 미리 공개되는 출처를 먼저 찾을 것이다.

셋째, 정확도는 목적이 아니라 수단이다. 0.667 분위 모델은 WAPE 로는 8% 나쁘지만 품절을 26% 줄였고, MPC 는 탐욕보다 덜 움직여서 비용을 낮췄다. 모델을 평가하는 숫자와 모델이 쓰이는 곳의 숫자가 다를 때, 둘을 같이 보여 주는 것이 모델을 만든 사람의 일이다.

넷째, LLM 은 숫자를 만드는 자리가 아니라 구조를 만드는 자리에 두어야 했다. 뉴스에서 유형과 지역과 심각도를 뽑는 일, 질문을 도구로 연결하는 일, 근거를 찾아 설명하는 일에는 잘 맞았다. 수요가 얼마나 변할지는 끝까지 묻지 않았고, 그래서 결과를 검증할 수 있었다.

마지막으로, 안 된 것을 지우지 않는 것이 가장 오래 남는 자산이었다. 철회한 주장, 나빠진 실험, 손으로 쓴 예시 답변이라는 사실을 모두 파일과 문서에 남겼다. 그 덕분에 이 글의 숫자를 하나하나 저장소와 대조할 수 있었다.
